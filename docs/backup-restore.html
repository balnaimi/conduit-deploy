Data Safety

Backup & Restore

How to protect your data, restore from a backup, or migrate to a new server.

📋 Scenarios

  1. What's in a Backup — Everything the backup includes
  2. Create a Backup — Save your current state
  3. Scenario A: Restore on Same Server — Roll back or recover
  4. Scenario B: Migrate to a New Server — Move everything to a different machine
  5. Best Practices — Backup tips and automation

1. What's in a Backup

Every backup is a single .tar.gz file stored in /opt/conduit-backups/. It includes:

ComponentWhat It Contains
DatabaseAll rooms, messages, user accounts, encryption keys
Media filesUploaded images, videos, documents
Configuration.env, docker-compose.yml, conduit.toml, Caddyfile
TLS certificatesLet's Encrypt certs and Coturn TLS files
SecretsRegistration token, TURN credentials
Pinned image versionsSHA256 digests of the exact Docker images that were running
🔒 Version Pinning: The backup saves the exact Docker image versions (SHA256 digests) that were running. When you restore, it pulls those exact same images — not a newer version. This means your restore is a perfect rollback, not "restore data + random new software."
📁 Storage Location: Backups are stored in /opt/conduit-backups/, which is separate from the installation directory (/opt/conduit/). This means:
  • Backups survive uninstall
  • Backups survive if the installation gets corrupted
  • You can safely delete and reinstall without losing your backups

2. Create a Backup

From the main menu: 5 (Services) → 7 (Backup with version pinning)

# The script performs these steps:

1. Checks disk space (warns if not enough room)

2. Offers to clean up old backups:
   "You have 3 old backups. Delete old backups? Keep only the latest 2. [y/N]:"

3. Saves the exact Docker image versions:
   ✅ conduit: matrixconduit/matrix-conduit:latest → 4078e80577cc...
   ✅ caddy: caddy:2-alpine → fce4f15aad23...
   ✅ coturn: coturn/coturn:alpine → 229f87ef2428...

4. Creates the backup archive:
   ✅ Backup saved: /opt/conduit-backups/conduit-backup-2026-03-15-180609.tar.gz (8.0K)
💡 When to backup:
  • Before updating containers (the script offers this automatically)
  • Before making any configuration changes
  • Regularly, as part of your maintenance routine
  • Before migrating to a new server

3. Scenario A: Restore on Same Server

Use case: An update broke something, you want to roll back to a known-good state, or you accidentally deleted data.

When Conduit is Still Installed

From the main menu: 5 (Services) → 8 (Restore from backup)

# The script shows available backups:
Available backups:
  -rw-r--r-- 1 root root 4.3K Mar 15 18:06 conduit-backup-2026-03-15-180609.tar.gz
  -rw-r--r-- 1 root root 4.3K Mar 15 08:45 conduit-backup-2026-03-15-084550.tar.gz

Backup file path: /opt/conduit-backups/conduit-backup-2026-03-15-180609.tar.gz

# Confirmation required:
  ⚠️ WARNING: This will replace your current installation!
  All current data, accounts, and messages will be overwritten.

Type 'RESTORE' to confirm: RESTORE

The restore process:

  1. Stops current services
  2. Extracts backup files to /opt/conduit/
  3. Pulls the exact same Docker images from the backup (pinned versions)
  4. Starts services
  5. Verifies everything is running
# Output:
ℹ Restoring from backup...
✅ Files restored

═══ Restoring pinned image versions ═══
  Pulling images...
  ✅ conduit
  ✅ caddy
  ✅ coturn

ℹ Starting services...
✅ Restore complete! Services are running.

After Uninstall (No Installation Present)

If you uninstalled Conduit but your backups are still in /opt/conduit-backups/:

  1. Run the script — it detects Conduit is not installed
  2. Go to 5 (Services) — it shows only the Restore option
  3. Choose 8 (Restore from backup)
  4. Select your backup file and confirm
# Services menu when Conduit is not installed:
═══ Service Management ═══

  Conduit is not installed. Only restore is available.

  8) Restore from backup
  0) Back to main menu
💡 Good to know: After a successful restore, the main menu shows your domain and "● Running" status again. Run Health Check to verify everything is working.

4. Scenario B: Migrate to a New Server

Use case: Moving to a bigger server, switching providers, or setting up a disaster recovery copy.

⚠️ Important — Same Domain Required: Your Matrix server name is permanent. The backup contains your domain configuration. The new server must use the same domain — you can't change matrix.example.com to chat.example.com during migration.

Step 1: Create a Backup on the Old Server

Run the script on your old server and create a backup:

# On old server — Services → Backup
# Note the backup file path:
/opt/conduit-backups/conduit-backup-2026-03-15-180609.tar.gz

Step 2: Copy the Backup to the New Server

Use scp to transfer the backup file:

# From your local machine (or old server):
scp root@old-server:/opt/conduit-backups/conduit-backup-*.tar.gz /tmp/

# Then to the new server:
ssh root@new-server "mkdir -p /opt/conduit-backups"
scp /tmp/conduit-backup-*.tar.gz root@new-server:/opt/conduit-backups/
💡 Direct transfer: If both servers are accessible, you can copy directly: 
ssh root@old-server "cat /opt/conduit-backups/conduit-backup-*.tar.gz" | ssh root@new-server "mkdir -p /opt/conduit-backups && cat > /opt/conduit-backups/conduit-backup.tar.gz"

Step 3: Update DNS

Point your domain to the new server's IP address:

TypeNameOld ValueNew Value
Amatrixold-server-ipnew-server-ip
AAAAmatrixold-ipv6new-ipv6

Wait for DNS propagation (a few minutes to hours depending on your TTL).

Step 4: Run the Script on the New Server

# SSH into the new server:
ssh root@new-server-ip

# Download and run the installer:
curl -sL https://raw.githubusercontent.com/balnaimi/conduit-deploy/main/conduit-deploy.sh | bash

Step 5: Restore from Backup

The script detects Conduit is not installed. Go to Services → Restore:

# Main menu → 5 (Services)
═══ Service Management ═══

  Conduit is not installed. Only restore is available.

  8) Restore from backup
  0) Back to main menu

Choose: 8

# Select your backup:
Available backups:
  conduit-backup-2026-03-15-180609.tar.gz

Backup file path: /opt/conduit-backups/conduit-backup-2026-03-15-180609.tar.gz
Type 'RESTORE' to confirm: RESTORE

# The restore runs:
ℹ Restoring from backup...
✅ Files restored
  ✅ conduit pulled
  ✅ caddy pulled
  ✅ coturn pulled
ℹ Starting services...
✅ Restore complete! Services are running.

Step 6: Verify

Run Health Check (3) to confirm everything works on the new server. Then stop the old server to avoid conflicts:

# On OLD server — stop services to avoid split-brain:
ssh root@old-server
# Run the script → 5 (Services) → 2 (Stop)
# Or uninstall entirely: → 6 (Uninstall)
⚠️ Critical: Never run two servers with the same domain at the same time! Stop the old server before the new one starts accepting connections (or immediately after DNS switch). Running both can corrupt your database or confuse federation.

Step 7: TLS Certificate

The backup includes TLS certificates, but they're tied to the old server. Caddy will automatically request a new certificate for the new server within a minute of starting. You don't need to do anything — just verify with Health Check that the cert is valid.

5. Best Practices

PracticeWhy
Backup before updatesThe script offers this automatically. Always say yes.
Keep 2–3 backupsThe script offers to clean old ones. Don't keep 20 — but don't keep just 1.
Copy backups off-serverIf the server dies, local backups die too. scp them to your local machine or another server.
Test your restoreA backup you've never tested is not a backup. Try restoring on a test server.
Check backup sizeIf backups suddenly get much bigger or smaller, investigate.

Automate Off-Server Copies

Set up a cron job to copy backups to another location:

# Example: copy latest backup to another server daily at 3 AM
0 3 * * * scp /opt/conduit-backups/$(ls -t /opt/conduit-backups/ | head -1) user@backup-server:/backups/matrix/

Migration Checklist

☐ Create backup on old server
☐ Copy backup to new server (/opt/conduit-backups/)
☐ Update DNS to point to new server IP
☐ Wait for DNS propagation
☐ Run script on new server → Restore
☐ Run Health Check — all green
☐ Stop or uninstall old server
☐ Test login from a Matrix client
☐ Verify messages and rooms are intact
